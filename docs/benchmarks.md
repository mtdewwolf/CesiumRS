# CesiumJS parity benchmark

`scripts/bench.sh` times CesiumRS and CesiumJS on the same inputs, checks that both produce the CesiumJS fixture results, and writes `target/bench-results/report.md`: median time per pass, the ratio CesiumRS ÷ CesiumJS in the same kind of runtime (below 1× means CesiumRS is faster), first-pass (cold) times and any failed checks.

```bash
scripts/bench.sh              # full run, under a minute per setup
scripts/bench.sh --quick      # fewer, shorter samples
scripts/bench.sh --filter geometry
```

## Setups

| Setup | Runtime | Compared with |
| --- | --- | --- |
| `cesiumjs-node` | `@cesium/engine` 23.0.0 in Node | reference |
| `cesiumjs-chromium` | the same, bundled with esbuild, headless Chromium | reference for wasm |
| `cesiumrs-native` | `examples/parity_bench`, bench profile (opt-level 3) | `cesiumjs-node` |
| `cesiumrs-wasm-shipped` | `examples/parity_bench_wasm`, release profile (opt-level `s`, LTO) | `cesiumjs-chromium` |
| `cesiumrs-wasm-fast` | the same, bench profile (opt-level 3) | `cesiumjs-chromium` |

The wasm setups need `rustup target add wasm32-unknown-unknown`. The browser setups need Chromium at `$CHROMIUM_PATH` (default `/usr/bin/chromium`). Pages are cross-origin isolated, so `performance.now()` has fine resolution. Missing setups are skipped.

Fixture inputs are under `tests/fixtures`. The fixtures are small by design, so `tools/cesium/bench/inputs.mjs` generates tile-sized heightmaps and Draco meshes into `target/bench-inputs`, deterministically. Those have no recorded result. Instead, `compare.mjs` requires each CesiumRS checksum to match the CesiumJS checksum within 1e-9, relative. Each side computes the checksum the same way and in the same order: sums of output positions, vertices, indices or coordinates.

## Method

Both sides use the same procedure. The Rust version is in `examples/parity_bench/harness.rs`; the JavaScript version is in `tools/cesium/bench/harness.mjs`.

1. Decode the inputs (not timed).
2. Time the first pass (cold, in workload order).
3. Check the outputs against the fixture.
4. Double the passes per sample until a sample lasts 25 ms.
5. Warm up for 300 ms.
6. Take 15 samples.

The report shows the median time per pass and the nearest-rank p95. `--quick` uses 5 samples of 5 ms after a 50 ms warm-up.

How the two sides are kept comparable:

- The Rust option decoders in `examples/parity_bench/workloads.rs` mirror the replay suites in `tests/`. The JavaScript side imports the fixture generators' own `polygonOptions` and `filledOptions`. If a decoder drifts, the fixture check fails.
- The CesiumJS hot loops pass `result` scratch objects wherever the API accepts one. CesiumJS is measured the way careful code would call it.
- `createGeometry` mutates its options in CesiumJS, so every pass rebuilds them (array → `Cartesian3`). The Rust side clones its options every pass.
- CesiumJS decodes Draco through its real `decodeDraco` worker (draco3d's C++ compiled to wasm), minus `postMessage`. CesiumRS calls `workers::draco::decode_triangular_mesh` (pure-Rust `draco-core`), minus the JSON worker wrapper. Both decode the indices and all three attributes.
- Draco is Node-only for CesiumJS: the worker imports draco3d's Node.js build.

## CesiumJS engine drift

The fixtures were generated by CesiumJS in Node. Another JavaScript engine can disagree with them, and `compare.mjs` reports that under "CesiumJS engine drift" rather than as a failure.

For example, Chromium 153's `Math.exp(0.37)` is one ULP away from Node 22's. That shifts a few 12-bit quantized `HeightmapTessellator` vertex components by one step (5 of 62 fixture cases). CesiumRS follows Node's V8 (`core::js_math`), so it agrees with the fixtures on every platform.

## Files

- `examples/parity_bench/`: the native runner, the shared workloads and the harness.
- `examples/parity_bench_wasm.rs`: a raw C-ABI wasm build of the same workloads (no wasm-bindgen).
- `tools/cesium/bench/`: the CesiumJS workloads and harness, plus `node.mjs`, `browser.mjs`, `wasm-host.mjs`, `inputs.mjs` and `compare.mjs`.
- Results go to `target/bench-results/<setup>.json` and `report.md`.

Not measured yet: peak memory, download size, and the quantized-mesh, LERC, KTX2 and I3S workers.
